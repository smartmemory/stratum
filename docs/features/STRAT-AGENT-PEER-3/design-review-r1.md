NOT CLEAN

The architecture is feasible: a detached driver can own app-server stdio and forward authenticated peer input through `turn/steer`. The findings below concern the proposed contracts and their grounding, not the absence of implementation. Keep the separate driver unless accepting that a peer endpoint crash also terminates the run.

Reviewed 2026-09-25 against the current checkout. `codex --version` returned `codex-cli 0.155.1`. `codex app-server generate-ts --out /tmp/peer3-ts` exited 0 with no output. Generated bindings confirm `TurnSteerParams = {threadId, clientUserMessageId?, input: UserInput[], expectedTurnId}` and `TurnSteerResponse = {turnId}`. They also expose `turn/interrupt`. The [official app-server documentation](https://learn.chatgpt.com/docs/app-server#steer-an-active-turn) confirms active-turn-only steering, the turn-ID precondition, no new turn-start notification, and no policy overrides in steering. CLI help labels app-server experimental. No paid/model run was launched; the design's historical queue probe was not repeated and is not independently verified here.

1. **[high] Cancellation and normal shutdown need an explicit ownership contract.**

   **Evidence:** Design lines 61–63 and 85 assume group cancellation, clean driver exit, no orphans, and a cancelled poll result. `ts/src/connectors/background.ts:577-586` checks the group leader identity, sends one SIGTERM, and immediately returns `cancelled`; it does not wait or escalate. Polling at `background.ts:487-516` reports `running`, `complete`, or `error`, including `child_died_without_sentinel`; it has no `cancelled` variant. A persistent app-server also needs deliberate shutdown after its turn completes. Merely flushing the stream and exiting the driver does not establish child termination. The sidecar currently owns a separate group (`peer-sidecar.ts:72-75`), intentionally surviving run cancellation to notify subscribers.

   **Suggested fix:** Specify driver PID as metadata's group leader, app-server as its non-detached child, and sidecar in its own group. Define bounded graceful shutdown, reaping, and forced termination for normal completion, signals, startup failure, and driver/app-server failure; define who writes the single final sentinel and which outcome wins a completion/cancel race. Preserve the existing poll API and assert its precise error/exit-code outcome, or explicitly include a cancelled-result API change in scope. Add tests for ignored SIGTERM, cancellation during initialization and steering, MCP parent exit, driver death, and tool descendants that may use their own process groups. A no-orphan claim needs live process-tree evidence, not just proof that driver and app-server share a group.

2. **[high] Stream parity is underspecified enough to permit false success and incorrect accounting.**

   **Evidence:** Design lines 53, 61, 84 and 98 promise translation but provide no mapping. `background.ts:657-666` extracts text only from `item.completed` / `agent_message`, and adds usage only from `turn.completed` with snake-case counters. Generated `/tmp/peer3-ts/v2/ThreadItem.ts:33` uses `agentMessage`; `/tmp/peer3-ts/v2/Turn.ts:21-25` carries terminal status and error; `TurnCompletedNotification.ts:6` contains a turn, not usage. Usage arrives separately in `ThreadTokenUsageUpdatedNotification.ts:6`, with cumulative `total` and `last` snapshots (`ThreadTokenUsage.ts:6`) and camel-case counters (`TokenUsageBreakdown.ts:5`). Writing a zero sentinel for every `turn/completed` can misreport a failed/interrupted turn that already emitted text as successful. Summing cumulative snapshots overcounts; translating only completion loses usage entirely.

   **Suggested fix:** Add a mapping table for message items versus deltas, tool/progress items, usage snapshots, retryable versus terminal errors, and completed/failed/interrupted status to durable error records and sentinel codes. Specify deduplication and ordering, including that all output/accounting precedes the single terminal sentinel. Test multiple assistant messages, multiple usage updates, cached tokens, partial output followed by failure, interruption, malformed/truncated frames, and output backpressure. The real golden flow should assert text and nonzero accounting, not merely the result shape. Do not invent cost when the server does not report it.

3. **[high] Carrying approval policy without handling server requests can hang a run.**

   **Evidence:** The design's driver only describes client requests and server notifications (lines 53–67). `ts/src/config/types.ts:4` permits `on-request`, `on-failure`, and `untrusted`, in addition to `never`. Generated `/tmp/peer3-ts/ServerRequest.ts:19` includes command/file/permission approval requests, user-input requests, and MCP elicitation. These require client responses; they are not notifications that a stream adapter can ignore. The error harness does not cover them.

   **Suggested fix:** Define an unattended response policy for every relevant server-initiated request, with bounded handling and no automatic expansion of permissions. Either implement supported approval behavior, or fail early for unsupported policies with a clear, documented limitation. Include approval and elicitation fixtures in the acceptance criteria. Make initialization explicit as `initialize` response → `initialized` notification → thread/turn startup; the [official initialization contract](https://learn.chatgpt.com/docs/app-server#initialization) requires the notification omitted from the sequence at design line 53.

4. **[med] Thread-start policy parity is possible, but the claimed encoding is not yet specified correctly.**

   **Evidence:** Generated `/tmp/peer3-ts/v2/ThreadStartParams.ts:12-16` has direct `model`, `cwd`, `approvalPolicy`, and `sandbox`, plus a generic `config` object. It has no direct `effort`, `writableRoots`, or `networkAccess` fields. Explicit effort and full sandbox policy are available in `TurnStartParams.ts`; `SandboxPolicy.ts:7` distinguishes `readOnly`, `workspaceWrite`, and full access. Existing `codexExecArgs` sets `model_reasoning_effort` and `sandbox_workspace_write.network_access` / `writable_roots` (`ts/src/connectors/codex.ts:173-192`). In particular, its network flag is a workspace-write setting, not an unconditional read-only network grant.

   **Suggested fix:** Document exact payloads: either use thread `config` for the existing config keys, or place effort and the appropriate full policy in `turn/start`. Specify precedence against ambient configuration, all sandbox modes, writable roots and temp-directory defaults, and retain the full-access authorization check. Update the acceptance criterion from “all carried into thread/start” to the chosen mapping. Compare effective returned policy where available and use a focused live sandbox probe; comparing two locally built objects alone cannot prove that the server honored the settings.

5. **[med] Steering failure, run failure, and delivery uncertainty are conflated.**

   **Evidence:** Design line 89 requires every error case, including an `expectedTurnId` mismatch or IPC disconnect, to yield a terminal stream. That contradicts the sidecar-failure isolation rationale at line 77: rejection of one message should not terminate otherwise healthy work. The proposed `{msg_id, text}` / `{msg_id, ok, reason}` exchange does not specify deadlines, unique internal correlation, bounds, or shutdown arbitration. Existing callback handling can discard non-notice statuses at capacity (`peer-sidecar.ts:161-169`) and during shutdown (`peer-sidecar.ts:215-218`). A steer can be accepted just before the driver/channel dies, leaving delivery uncertain; “dropped” must not imply proven non-delivery in that case.

   **Suggested fix:** Separate run lifecycle from per-message lifecycle. Make no-active-turn and turn-ID mismatch message-level refusals; reserve terminal-stream failure for actual run failure. Use bounded pending requests keyed by an internal request ID and sender/msg_id, specify duplicate behavior and timeouts, and never blindly retry an ambiguously accepted steer. Define delivered as confirmed server acceptance, with explicit uncertainty detail for a lost acknowledgment. Retain accepted-message status callbacks through terminal cleanup. Test simultaneous senders, duplicate IDs, response loss after acceptance, delayed responses, callback saturation, and steer/completion races. Limit the post-completion refusal guarantee to the sidecar's linger window; after endpoint cleanup no receiver remains to send it.

6. **[med] The opt-in knob crosses an excluded foreground boundary, while background dispatch currently bypasses it.**

   **Evidence:** Design lines 45 and 73 exclude foreground changes but widen the shared `CodexTransport`/environment selector. `background.ts:181-185` directly builds `codexCommand`, without resolving transport. `codex.ts:249-254` resolves the shared knob and may force exec for process-group ownership; `codex.ts:280` sends every non-SDK value down `runExec`. Thus adding the enum value alone can make the same setting mean app-server in one path and silently exec in another. This is a design routing gap, not a complaint that the new route is unimplemented.

   **Suggested fix:** Specify selection at `startBackgroundRun`, including precedence of `options.env`, the injected-command test seam, peer registration disabled/unavailable, and foreground behavior. A smaller design is a background-only execution strategy plus a shared policy encoder, leaving the foreground SDK/exec transport union unchanged. Keep the separate driver and IPC: merging driver and sidecar saves one process, but sacrifices the stated crash-isolation benefit. No verified exec/SDK alternative in the reviewed code provides the required live input primitive. Add source/dist driver-launch, parent-detachment, and peer-registration-failure criteria; preserve best-effort registration and return `peerName` only under a defined readiness/discovery contract.
