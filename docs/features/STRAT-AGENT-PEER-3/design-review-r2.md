NOT CLEAN

1. **[high] Cancellation still has contradictory terminal rules (r1 #1; §2 versus §3).**

   **Evidence:** `design.md:81` requires exactly one sentinel per run, while `design.md:83` explicitly requires none on cancellation. `design.md:84` says the first terminal event wins, but `design.md:82` delays the completion sentinel until after child shutdown and reaping. Thus a completion followed by SIGTERM during that wait must both retain the completion outcome and exit without a sentinel under the stated rules. Conversely, cancellation followed by an `interrupted` notification conflicts with the unconditional sentinel-130 mapping at `design.md:101`. The source does not arbitrate this for the driver: `ts/src/connectors/background.ts:578-586` scans once, sends SIGTERM, and returns `cancelled`; it does not rescan after signalling. A sentinel appearing between that scan and the signal therefore does not necessarily produce `already_complete`, as the design claims. `ts/tests/connectors/background.test.ts:169-178` establishes only the ordinary cancel-without-sentinel case.

   **Suggested fix:** Define a single terminal claim shared by notification, signal, and failure handlers. If cancellation wins, suppress subsequent completion/error sentinels and exit without one after bounded cleanup; if completion wins, later signals may accelerate cleanup but cannot change the claimed result. State “at most one sentinel,” with the cancellation/driver-death exceptions. Distinguish the cancel API's immediate acknowledgement from eventual poll state, and qualify `already_complete` as requiring a sentinel visible to its initial scan. Add both event orders and cancel-during-reap to the design's acceptance criteria.

2. **[high] Several unattended responses are not valid for the request types they answer (r1 #3, §4).**

   **Evidence:** `design.md:133-136` assigns `decline` to both modern and legacy approval requests, and `cancel/decline` to user-input requests. Modern command/file approvals support `{decision:"decline"}`, but legacy `ExecCommandApprovalResponse` and `ApplyPatchApprovalResponse` use `ReviewDecision` (`/tmp/peer3-ts/ExecCommandApprovalResponse.ts:6`, `ApplyPatchApprovalResponse.ts:6`); that union has `{denied:{rejection:string}}` and `abort`, not `decline` (`/tmp/peer3-ts/ReviewDecision.ts:10`). Permissions responses require `permissions` and `scope`, not a decline decision (`/tmp/peer3-ts/v2/PermissionsRequestApprovalResponse.ts:7-11`). Tool user input requires an `answers` map and exposes no cancel/decline variant (`/tmp/peer3-ts/v2/ToolRequestUserInputResponse.ts:9`). These are separate members of the actual server-request union (`/tmp/peer3-ts/ServerRequest.ts:19`). The new table therefore does not yet establish its claim that all these requests receive a valid immediate response.

   **Suggested fix:** Specify typed result objects per method: modern approvals `{decision:"decline"}`; legacy approvals a valid denial/abort value; permissions an empty grant with explicit scope, such as `{permissions:{},scope:"turn"}`. For tool user input, define and verify an empty-answer policy or an explicit JSON-RPC unsupported-request error with a bounded failure path. Keep elicitation separate, including its required nullable fields. Make the fixtures validate the generated response types and request completion, rather than merely that something was written.

3. **[high] The revised lifecycle still has no terminal path for startup rejection or unexpected app-server exit (r1 #1/#2, §2–§4).**

   **Evidence:** `design.md:82-85` defines normal completion, cancellation, and driver death, but not app-server spawn failure, a rejected `initialize`/`thread/start`/`turn/start`, or app-server EOF/exit before `turn/completed`. The handshake at `design.md:111` only lists the successful sequence. `design.md:103` fails after three consecutive malformed/truncated frames, which cannot cover a single truncated frame followed by EOF. This matters because metadata now identifies the driver (`design.md:79`): the unchanged poller returns `running` while that driver is alive (`ts/src/connectors/background.ts:487-490`), regardless of whether its app-server has exited. “Only run failures … write a terminal sentinel” (`design.md:143`) does not define detection, cleanup, or the result for these failures. The current exec wrapper, by comparison, records the command's exit (`ts/src/connectors/background.ts:54-57`).

   **Suggested fix:** Add explicit startup-response error, spawn error, transport EOF/exit, and bounded initialization-timeout transitions to the terminal claim. Unexpected EOF must be terminal regardless of the malformed-frame count. Specify the durable error record, nonzero sentinel, bounded child shutdown/reaping, and driver exit; distinguish expected transport closure during an already-claimed completion/cancellation. Add rejection-at-each-handshake-step and EOF-before-completion fixtures. This is a missing design contract, not a request to implement the driver in this review.

4. **[med] Callback retention has no capacity/admission contract that can preserve accepted steer results (r1 #5, §5).**

   **Evidence:** `design.md:157` bounds pending steers to eight, and `design.md:160` promises retained status callbacks through capacity pressure and cleanup, but never says whether the pending slot remains reserved until the callback attempt finishes. Eight concurrent steers can complete repeatedly while callback sockets remain held, accumulating more than 32 queued results. Today's scheduler has eight active attempts and 32 queued slots (`ts/src/connectors/peer-sidecar.ts:164-176`), and reserves the queue for up to 32 idle notices by evicting non-notices. The saturation and shutdown cases are concrete in `ts/tests/connectors/peer-sidecar.test.ts:698-725,743-755`. Simply treating steer statuses “like accepted idle notices” is insufficient: notice callbacks to the same address are coalesced (`peer-sidecar.ts:162-163`), which would lose distinct message results, and 32 notice reservations already consume the existing queue. The revised lifecycle AC at `design.md:191` tests pending-steer overflow but omits callback saturation.

   **Suggested fix:** Specify separate result reservations or keep each accepted steer's admission slot through its bounded callback attempt. Preserve idle-notice reservations, correlate retained results by message/request rather than destination alone, and define best-effort handling for unaccepted busy/refusal traffic. During shutdown, settle accepted pending requests before draining their reserved result callbacks. Add a fixture with fast steer acknowledgements, held callback sockets, 32 idle subscriptions, multiple messages from one sender, and terminal cleanup; require every accepted result to receive an attempt within bounded memory/time.
