## Problem

The TS engine has one parallel primitive, native `fanout`, but currently executes every fanout item itself through its configured connector (`engine.ts:890-1253`). Compose needs the other ownership model already used for ordinary TS steps: Stratum schedules work, the client executes it, and the client reports the result.

The Python-era `parallel_dispatch` surface supplied that ownership model through four special tools and two lifecycles:

- consumer dispatch: compose created worktrees, ran agents, captured/applied diffs, then called `parallelDone` (`../compose/lib/build.js:4499-4918`);
- server dispatch: compose called start, polled task state, optionally merged returned diffs, then called advance (`../compose/lib/build.js:3693-4003`).

Porting those tools would duplicate a lifecycle that TS already expresses as `plan -> ready[] -> step_done`. This feature instead makes dispatch ownership a property of native fanout. It must preserve current engine dispatch as the default, retain per-item retry/ensure/require semantics, keep state restart-safe, and let compose continue to own worktrees and merges without teaching the engine about compose diffs.

## Metadata boundary (governs D2–D5; added 2026-07-12)

The producer owns **authoring intent** (the source spec it wrote). The engine owns the **effective run revision** and **every effective dispatch descriptor**. The earlier cut — "producer derives statically-declared metadata from its own local spec; engine surfaces only runtime-resolved state" — is too coarse: metadata can be statically declared yet impossible for a restart-safe or stateless consumer to *locate* (consumer-fanout stage cursors are the proof case, D2). Corrected rules for this feature:

1. The **effective run revision IS the persisted effective spec** — the validated, default-injected spec the engine already stores in run state at plan time (today's persisted `spec`, `state.ts:161`; e.g. `dispatch: "engine"` injection makes it differ from the submitted object). `plan` and `resume` return its **`revisionDigest` on every response variant**, persisted in run state alongside the spec, and every consumer descriptor echoes it. That is the entire v1 verification surface: the producer pins the digest at plan time and checks descriptor echoes — no other tool response carries it. There is deliberately **no fetch-by-digest surface in v1**: descriptors are self-contained (rule 2), so nothing a consumer needs is locked behind a lookup — the digest pins and audits, it does not resolve. This makes the "compile boundary" real rather than assumed.
2. Every consumer-fanout `ready` entry is a **self-contained, token-fenced effective dispatch descriptor** (D2) — the contract for one authorized execution, not a spec mirror.
3. **Contract invariant:** every issued dispatch has a *fixed* effective output contract; it may originate at compile time or via a governed runtime plan revision, but **cannot change after issuance**. (This supersedes any "output contracts are always compile-time-fixed" phrasing, which needlessly blocks tool-discovery / planner-synthesised / heterogeneous-fanout workflows.)
4. Topology-preserving runtime decisions (model choice, cache hit, budget-admission) surface as **events / policy provenance**, not hidden state (consistent with the STRAT-TS-PORT observability contract). Topology- or contract-changing decisions require a **new explicit plan revision + authored→effective origin map + audit event** — "optimization" does not make graph mutation internal. (That runtime plan-revision mechanism and origin map are FUTURE scope, stated here as the governing principle: v1 ships no runtime revision beyond the existing gate `revise`, which mutates no topology.)

This section is the reason D2 changed; keep D3–D5 consistent with it.

## Decision record

### D1. `dispatch` selects execution ownership; `engine` remains the default

`fanout.dispatch` is `"engine" | "consumer"`, defaulting to `"engine"`. An omitted field preserves current engine-dispatch **behavior** unchanged: engine workers enforce `concurrency`, invoke connectors, optionally create worktrees, capture patches, run `pre_merge`, and merge sequentially. (Behavioral, not byte-level: at the Phase-2 flag-day the persisted effective spec gains the injected `dispatch: "engine"` default and every client-executed ready entry gains its universal fencing token, so serialized surfaces move even for specs that never use consumer mode.)

With `dispatch: "consumer"`, the fanout step still owns enumeration, concurrency, attempts, budgets, ensures, persistence, `require`, output ordering, and downstream advancement. Only execution ownership moves: executable item stages appear in the ordinary `ready[]` response and the consumer reports them through `stratum_step_done`.

This is an extension of the TS execution model, not a second parallel subsystem and not a revival of `parallel_dispatch`.

### D2. A ready consumer-fanout item is a self-contained, fenced dispatch descriptor

**REVISED 2026-07-12 (codex architecture critique, code-verified).** The original D2 assumed a bare `ReadyStep` (`{id, do, agent, attempt, epoch, previousFailure}` — `engine.ts:79`) plus producer-side reconstruction of stage/contract from the local spec. That is not restart-safe. A multi-stage consumer item reuses one runtime id across stages that can each declare a different `out` contract and `when` (`schema.ts:33`); `attempt` is cumulative across stages (`engine.ts:1119`); and the engine alone owns the stage cursor. A stateless or restarted consumer seeing `review/2` cannot locate which stage — hence which contract — applies without re-implementing engine state recovery. **Statically-declared does not imply producer-locatable** (the general boundary — see "Metadata boundary" above).

The runtime id stays `<fanout-step-id>/<zero-based-item-index>` (opaque, like subflow `<parent>/<child>` — `engine.ts:1621-1637,1708-1710`), not a legal authored `StepId`. But a consumer-fanout `ready` entry is a **self-contained effective dispatch descriptor**, not a bare `ReadyStep`. It carries, in engine-native terms (never compose vocabulary):

- `dispatchToken` — opaque, unique per issuance (see fencing below);
- authored origin: `flow`, `step`, and the fanout `stage` + `itemIndex`;
- the rendered instruction (`do`);
- effective `agent` and execution policy;
- the **effective output contract for the current stage, carried as its CLOSURE** (AMENDED 2026-07-16, round 3): the root contract id plus the raw shape of every named contract reachable from it — contract fields may reference other named contracts, which validation resolves recursively (`validate.ts:62,145`), so inlining only the root shape (what `engine.ts:1150` hands the connector today) is NOT self-contained for a stateless consumer. `contractDigest` is computed over the canonical serialization of that closure. A hash alone cannot tell a restarted or stateless consumer what shape to produce; carrying the closure IS the execution contract, not spec-mirroring. A stage that declares no `out` (`FanoutStageSchema.out` is optional — `schema.ts:33`) carries `contract: null` and `contractDigest: null`: the report is accepted without shape validation, exactly as engine dispatch omits `outSchema` for contract-less stages. The FIELDS are always present; a contract is not always declared — the "fixed effective output contract" invariant reads "fixed, possibly fixed-absent," and `over`/`steps` source compatibility holds;
- `attempt` and structured `previousFailure`;
- the effective run-revision digest (see IR changes).

This is not spec-mirroring — it is the contract for one authorized execution. The consumer executes exactly what the descriptor states and never re-derives stage/contract from a local cursor. Engine-dispatch fanout is unchanged; only the consumer-dispatch `ready` entry gains these fields. `locateStep` still resolves the root parent then discriminates by construct (`run` → child step; consumer `fanout` → numeric item index).

**Fencing must be real on the wire — at the 07-12 revision it was not.** `stepDone`'s stale check only fired when the caller supplied `expectedEpoch` (`engine.ts:365`), but the MCP server passed no epoch and the request schema had no epoch field, so over MCP no stale report was ever rejected. Phase 1 (landed 2026-07-15, surface 7) closed the live revision-staleness hole: `step_done` now declares optional `epoch`, the server forwards it to `expectedEpoch`, and compose echoes every ready entry's epoch. The end state is per-issuance: `step_done` must echo the `dispatchToken`, and the engine rejects any report whose token is not the current issuance for that item. This is a REQUIRED `step_done` request-shape addition — the earlier "no request-shape change" claim was wrong.

### D3. Existing failure machinery owns retry and bounce

Reporting `result.failure`, failing the stage output contract, or failing an engine-evaluable `ensure` records a normal fanout attempt. If attempts remain (`stage.attempts ?? fanout-step.attempts ?? 2`), that same item becomes ready again with structured `previousFailure`; other successful items are not re-run. When attempts are exhausted, the item becomes terminal `failed` and its concurrency slot is released.

The consumer may run worktree-local gates before reporting. A local gate, agent, or diff-capture failure is reported as `result.failure` and therefore follows the same retry path. The engine continues to evaluate output expressions and judged ensures after `step_done`. It cannot truthfully evaluate filesystem predicates inside a consumer-owned worktree; validation rejects `file_exists`/`file_contains` on consumer fanout stages when `isolation: "worktree"`. The SAME rejection applies to stage `when` conditions (AMENDED 2026-07-16): engine dispatch evaluates each stage's `when` against the item's worktree (`engine.ts:1116`), which the engine cannot see in consumer mode, so a filesystem-dependent `when` on a consumer worktree stage is rejected at validation with the same targeted diagnostic; state-evaluable `when` expressions remain legal. Worktree-local verification belongs in the consumer's gate and is reported as a failure.

No `parallelDone`, bounced-task envelope, or fanout-specific done tool is added.

### D4. `require` is evaluated once all items are terminal

The engine does not settle early when `any` or `N` first becomes true: already-dispatched consumer work has no cancellation handshake, and final output must preserve one position per input item. It waits until every item is `succeeded`, `failed`, or `skipped`, then computes:

- `all`: required successes = input length;
- `any`: required successes = 1;
- positive integer `N`: required successes = `N`.

Only `succeeded` counts. A final-stage skip produces `null` in the ordered output and does not count. Thus an empty fanout satisfies `all`, but fails `any` and every positive `N`. If the threshold is not met, the fanout takes its existing terminal/on-fail path; it never retries the whole batch. If met, output is the existing index-aligned array (`output | null`) and the fanout step succeeds.

### D5. Merge is an explicit downstream gate

Consumer mode never creates worktrees, captures patches, runs engine-side `pre_merge`, applies diffs, or interprets merge status. The consumer owns those artifacts and operations.

The deferred merge handshake is composition: a merge gate is authored immediately after the fanout. Once `require` is satisfied, the fanout succeeds and the gate enters `waiting_gate`. The consumer applies its retained diffs in its chosen deterministic order, then resolves the existing gate:

- `approve`: merge was clean; advance to the post-merge step;
- `revise`: merge needs repair; route to the gate's authored repair/re-dispatch target, bounded by existing `max_rounds`;
- `kill`: merge cannot safely continue.

This is preferred over making the fanout wait for a new merge-status report because a waiting fanout would conflate two owners, require a new persisted state and MCP status, and recreate `parallelAdvance`. The gate makes the side-effect boundary visible in IR, is auditable through existing events, and reuses the existing bounded revision protocol. A consumer fanout that writes files MUST be followed by such a gate; this is an authoring/compose invariant, not something the engine can infer from agent output.

**A gate decision is itself a client report, and is fenced like one (AMENDED 2026-07-15b).** `stratum_gate_resolve`'s request carries only `{runId, stepId, decision}` and `gateResolveLocked` checks no issuance identity (`engine.ts:587`), while revisions bump descendant epochs the gate path ignores (`engine.ts:1485`). Under `max_rounds` the same gate id re-enters `waiting_gate` across rounds, so a delayed or duplicate `approve`/`kill` from an earlier round could resolve a later round's wait — advancing past a merge whose artifacts were never applied. D5 is only sound if the decision channel is fenced, so Phase-2 fencing covers gates: every entry into `waiting_gate` mints a per-issuance **`gateToken`**, exposed wherever the waiting gate is surfaced, and `gate_resolve` must echo it — same mint/persist/rotate lifecycle (see Engine mechanics) and same flag-day as `dispatchToken`. The token surfaces through `stratum_audit`'s `steps` serialization — the exact surface the consumer already uses for gate discovery (a bare `running` response → audit fetch → scan `steps` for `waiting_gate`; compose `build.js` ~1929) — not through event payloads (`gate_waiting` stays `stepId`-only), so the frozen `events.json` claim below stands. Discovery is therefore MANDATED as audit-fetch: discover the waiting gate, read its `gateToken` from the audit step entry, echo it on `gate_resolve`.

## IR & contract changes

### Specification boundary (r6 — scope decision)

Six grounded review rounds converged the SEMANTICS of this design (fencing, tokens, generations, journal invariants, recovery rules) while repeatedly requesting ever-deeper wire/file encodings (exact descriptor property names, closure JSON layout, policy field shapes, journal file format). Those encodings are deliberately NOT specified further in prose — per repo planning standards, data shapes live in contract files, not documents. The FIRST implementation step authors the frozen contracts as files: the `ready` element shapes (ordinary entry + consumer descriptor, tagged grammar), the descriptor's contract-closure layout, the effective-policy fields (`isolation`/`merge`/`pre_merge` as consumer instructions), and the `errors` registry — under `ts/contracts/`, code-reviewed with the implementation. The prose field lists in this document are non-normative summaries; the contract files are the freeze. Likewise, the compose artifact-journal file format ships with the compose slice, and the crash-test suite in the test plan — not further prose iteration — is the arbiter of the recovery protocol's correctness.

### IR

`ts/src/ir/schema.ts` adds one optional strict field:

```ts
dispatch: z.enum(["engine", "consumer"]).default("engine")
```

Defaulting must occur in the validated value so persisted specs and all engine branches observe `engine`; raw specs without the field remain valid. No new step kind is introduced. `over`, `steps`, `concurrency`, `isolation`, `require`, `merge`, and `pre_merge` remain source-compatible. In consumer mode, `isolation`/`merge`/`pre_merge` are consumer instructions; the engine must not execute them.

Semantic validation adds:

- consumer + worktree + stage filesystem ensure: reject with a targeted diagnostic;
- consumer + worktree + filesystem-dependent stage `when` (`file_exists`/`file_contains`): reject with the same targeted diagnostic — detection inspects the expression AST, so file predicates nested inside boolean expressions and `{expr: ...}` forms are caught, not just top-level calls;
- consumer + `isolation: "worktree"` REQUIRES a gate step as the fanout's direct successor in the flow (r6 — promotes D5's authoring invariant to a validated rule via its machine-checkable proxy: worktree isolation signals writing intent). That validated successor gate is the one whose resolution releases the commit/revert lifecycle guard; a consumer fanout WITHOUT worktree isolation carries no post-settlement guard extension — the guard lifts at fanout settlement (no-gate behavior is thereby specified, not heuristic);
- consumer fanout in a subflow remains rejected because fanout is currently root-only;
- numeric `require > item count` is legal and deterministically fails at runtime, as today.

### MCP surface

`stratum_step_done.request.stepId` is already `string`, so scoped `<fanout>/<index>` ids need no id-shape change. But consumer fanout requires two REAL surface additions (the earlier "no request-shape change" claim was wrong):

- `stratum_step_done.request` gains a **`dispatchToken: string`** that the consumer echoes from the descriptor it was handed. The engine rejects a report whose token is not the item's current issuance (D2 fencing).

  **Fencing scope (AMENDED 2026-07-15, post whole-port review).** The original cut — "for ordinary/engine-owned ids the token is optional/ignored" — would have CEMENTED the very defect this fencing exists to close: the 2026-07-15 adversarial review confirmed ordinary client-executed steps are equally unfenced over MCP (the engine's `expectedEpoch` staleness check exists but the server never supplies it, so a stale or duplicate report can satisfy post-revision readiness — `server.ts:94`, `mcp-surface.json` step_done request). Fencing is therefore UNIVERSAL, delivered in two phases:

  - **Phase 1 (landed 2026-07-15, pre-fanout, surface 7):** `step_done.request` declares optional `epoch`; the server forwards it to the engine's existing `expectedEpoch` check; compose echoes `ready[].epoch` on every report. A mismatched echo is rejected; a missing echo is still accepted (migration compat). This closes the live revision-staleness hole for the only current consumer. Per-revision epochs do not fence same-epoch duplicates (late retry reports) — acceptable for a sequential single-report consumer, not as the end state.
  - **Phase 2 (this feature):** every client-executed issuance — ordinary step, subflow child, consumer-fanout stage — carries a per-issuance `dispatchToken` in its ready entry; `step_done` must echo it; the engine rejects missing or mismatched tokens once compose echoes tokens (flag-day on the coordinated `develop` branches, before the atomic merge). Gate waits are issuances too (AMENDED 2026-07-15b): every `waiting_gate` round mints a `gateToken`, and `stratum_gate_resolve.request` gains the required echo at the same flag-day. The token is strictly stronger than the epoch (per-issuance beats per-revision, closing late-retry duplicates too); the Phase-1 `epoch` request field is then subsumed and retired with a surface bump. Only consumer-fanout entries carry the full dispatch DESCRIPTOR; ordinary ready entries gain just the token.
- Each consumer-fanout entry in `ready` is a **dispatch descriptor object** (D2 fields: `dispatchToken`, authored origin incl. `stage`/`itemIndex`, rendered `do`, effective `agent`/policy, effective output-contract id + inline canonical shape + digest, `attempt`/`previousFailure`, run-revision digest), not a bare `ReadyStep`. `ready` stays an array; its consumer-fanout element shape is richer. Ordinary/subflow ready entries are unchanged **except that they gain `dispatchToken`** (Phase 2 above).
- `stratum_plan` and `stratum_resume` expose **`revisionDigest` on every response variant** (Metadata boundary rule 1: the revision IS the persisted effective spec; the digest is persisted alongside it in run state). Consumer descriptors echo it; no other tool response carries it in v1.
- **Digest/token concretes (AMENDED 2026-07-15b, r3-refined):** every digest is SHA-256 over a canonical JSON serialization (lexicographically sorted keys, no insignificant whitespace, UTF-8); tokens are opaque unique strings persisted in run state (see Token lifecycle). Persisted and wire field names are exactly: `revisionDigest` (effective run revision), `contractDigest` (the stage output-contract CLOSURE; `null` when the stage declares no `out`), `dispatchToken`, `gateToken`.
- **The frozen shape language gains array-element shapes (AMENDED 2026-07-16, round 3; r4-specified):** `ready` is currently declared as bare `"array"` and the contract checker verifies only `Array.isArray` (`contracts.ts:36,89`), which cannot hold the descriptor contract. The shape grammar gains exactly two constructs with a concrete tagged JSON encoding (r5): **`{"$array": <shape>}`** and **`{"$oneOf": [<shape>, ...]}`** — `$`-prefixed keys are reserved grammar tags, illegal as record field names anywhere in the surface (today `Shape` is only `string | object-record` and every non-string node is read as an object shape — `contracts.ts:3,36`). `$oneOf` matching is strict and COMPLETE: a value matches iff it matches exactly one variant as a whole strict object — required fields present AND undeclared fields rejected (required-fields-only matching would let the richer consumer descriptor also satisfy the ordinary `ReadyStep` variant, `engine.ts:79`). Field names suffixed `?` are optional (r6): strictness rejects UNDECLARED fields, never absent optional ones. `ready` becomes `{"$array": {"$oneOf": [<ordinary entry>, <consumer dispatch descriptor>]}}` with both element shapes declared in full — ordinary entry: `id`/`do`/`agent`/`attempt`/`dispatchToken`/`previousFailure?` with its complete failure shape (`ReadyStep` declares it and emits it on retries and routed work — `engine.ts:79`, `engine.ts:1529`; omitting it would make every ordinary retry fail the frozen contract) (+ `epoch` until retired); consumer descriptor: those plus `stage`/`itemIndex`/`generation`/contract closure/effective policy/`revisionDigest`. The contract checker and the shared JSON-schema translator (`server.ts:229`) implement the SAME tagged grammar. This rides the Phase-2 surface bump.

Background consumer dispatch (DEFERRED to the follow-up — see Background flows v1 scope) also adds: the `running` response for `stratum_flow_bg_poll` gains optional `ready: array` (of the same descriptor shape). Its `bg.status` remains a contract `string` and may be `awaiting_consumer`. In v1 the only bg-facing change is the submission-time rejection of consumer-dispatch specs.

Because the frozen surface changes, increment `surface` and update both P4/P5 exact-version assertions. No fanout-specific MCP *tool* or response *status* is added — the changes are additive request/response fields on existing tools.

### Events

No new event kind is needed. Consumer mode reuses:

- `fanout_item_ready` when a slot exposes an item stage;
- `fanout_attempt_result` when `step_done` accepts an attempt;
- `fanout_item_skipped` for a skipped stage;
- `fanout_ledger_debit` for dispatch/usage/judge debits;
- ordinary `result`, `gate_waiting`, and `gate_resolved` at aggregate boundaries.

`fanout_item_dispatched` remains engine-dispatch-only: the engine cannot know when an external consumer actually starts work. Therefore `ts/contracts/events.json` needs no shape or version change. `flow_poll` and `flow_bg_poll` remain the canonical durable progress spine; compose-local worktree/diff narration stays compose-local.

## Engine mechanics

### Scheduling and state

`FanoutItemState` gains a consumer-ready state plus persisted `stage`, `epoch`, and `dispatchToken` fields. Ordinary `StepState` likewise gains a persisted `dispatchToken` (every client-executed issuance is fenced, not just fanout items — `state.ts:122`), and gate-bearing steps persist the current round's `gateToken`; `stratum_audit`'s step serialization exposes both for non-terminal issuances. Terminal-succeeded items additionally persist **`acceptedDispatchToken`** — the issuance whose report terminalized them — exposed through audit as the consumer's unambiguous reconciliation target (r4; without it, a consumer cannot tell whether ITS prepared attempt or a later one succeeded). Initialization remains index ordered. For consumer dispatch, the scheduler promotes at most `concurrency` pending items to `ready`; a slot stays assigned across all stages of an item, matching the current worker model. A terminal item releases a slot and immediately promotes the next pending item.

Rendering uses the same `${item}` and `${prev}` context as engine dispatch. Dispatch budget is reserved exactly once when an item stage first becomes ready, not on every `plan`, `resume`, or poll that returns the same readiness. Usage settlement, output-contract validation, ensure evaluation, attempt recording, and budget terminalization are factored from ordinary `stepDoneLocked`/`executeFanoutItem` so the two dispatch owners cannot drift semantically.

Settlement runs only under the per-run lock after the last item terminalizes. It performs `require`, records the aggregate result, persists, and advances. Its merge branch is guarded by `dispatch === "engine"`.

### Locking and persistence

Consumer execution has no in-process worker and no retained mutable run object outside the lock. Enumeration, readiness promotion, every `step_done`, and settlement are lock-wrapped and atomically persisted. A restart simply returns persisted ready items; terminal items never redispatch. The per-issuance token — not the per-revision epoch — rejects duplicate and late reports (CORRECTED 2026-07-15b: an epoch cannot fence same-epoch duplicates; that is exactly why Phase 2 exists).

**Token lifecycle (AMENDED 2026-07-15b; binds `dispatchToken` and `gateToken` alike):**

- **Mint per issuance:** every promotion to `ready` is a new issuance — first dispatch, each retry, each stage advance, each re-issue after a plan revision — and every entry into `waiting_gate` is a new gate issuance per round.
- **Persist before expose:** the token is written to durable run state before any response or poll can carry it.
- **Stable within an issuance:** `plan`, `resume`, polls, and process restart return the SAME token while the issuance stands; re-reading readiness never re-mints and never re-debits budget.
- **Rotate on any reissue:** the superseded token is rejected forever.
- **Checkpoint revert rotates:** checkpoints snapshot `steps` (`state.ts:148`) and revert restores them (`engine.ts:473`), which would resurrect pre-revert tokens; `revert` therefore re-mints the token of every restored non-terminal issuance after restore, so a report or gate decision minted before the revert can never satisfy post-revert readiness.
- **Generations never roll back (r4):** the run carries a monotonic **generation counter persisted OUTSIDE checkpoint snapshots** — revert never restores it. Every fanout item (re-)enumeration — initial, post-revise, post-revert — advances it and stamps item state with the current generation; consumer descriptors expose it. Item epochs roll back with `steps` and so CANNOT identify artifact generations; the counter can, which is what makes consumer-retained evidence collision-free across reverts.
- **Cancellation invalidates:** a cancelled run promotes no further issuances and its outstanding tokens are never accepted.

The foreground `commit`/`revert` fanout guard remains conservative while either dispatch mode has a running fanout — and for CONSUMER fanout with worktree isolation the guard extends through the downstream merge gate (r5, r6-anchored): `stratum_commit` and `stratum_revert` are REFUSED from the first consumer issuance until the fanout's VALIDATED direct-successor gate (see semantic validation) resolves or the run terminalizes; consumer fanouts without worktree isolation release the guard at fanout settlement. Checkpoints at waiting gates and reverts of terminal runs are both legal today (`engine.ts:451`, `engine.ts:1804`; pinned by `p5.test.ts:128,149`), so a checkpoint could otherwise capture a succeeded generation plus its waiting merge gate, and reverting it after `revise`/cleanup would restore a gate whose evidence is permanently `superseded` or deleted — the generation counter cannot help because nothing re-enumerates. v1 forbids the whole class rather than designing checkpoint-aware artifact reactivation; the bg follow-up may revisit retention semantics. Revision rotates the fanout's and all items' tokens (and still bumps epochs); stale consumer reports fail exactly like stale ordinary-step reports.

### Background flows

**v1 scope (RESOLVED 2026-07-15b; was Open Question 3): foreground only.** Compose's first consumer is the foreground `runBuild` pump, so background consumer dispatch is DEFERRED to a follow-up feature. In v1, `stratum_flow_run_bg` REJECTS a spec containing `dispatch: "consumer"` at submission with a typed diagnostic, covered by a frozen contract test — it must never silently connector-dispatch consumer work, and the public `stepDone` bg ownership guard (`engine.ts:333`) stays intact. The rejection travels the EXISTING validation-failure channel as a genuinely typed error (r3-refined): the server maps `SpecValidationError` to an MCP protocol error whose `data` payload carries the structured validation errors plus a stable machine-readable code — `consumer_dispatch_bg_unsupported` — because a regex-pinned message is not a typed contract (`SpecValidationError`'s public message is just "spec validation failed", `engine.ts:183`). The error-code registry is frozen alongside the surface as a new top-level `errors` section in `mcp-surface.json` — `{ "<code>": { "data": <shape> } }` — modeled in `McpSurface` (which today models only tools — `contracts.ts:5`) and asserted by a p5 test against the ACTUAL MCP error `data` payload (protocol errors bypass `assertToolResponse` because the dispatcher rethrows — `server.ts:152` — so the test intercepts the JSON-RPC error itself, not a tool response). `stratum_flow_run_bg`'s frozen response set (`running` only) still gains no new variant, consistent with the "no new response status" claim; the frozen test pins the CODE. The `flow_bg_poll.ready` / `awaiting_consumer` additions named elsewhere in this document land with that follow-up, not v1. The semantics below are the committed design for the follow-up:

The detached driver must not execute consumer items through its connector. When its ready set contains consumer fanout ids it records `bg.status = "awaiting_consumer"`, stops its drive loop, and exposes those entries through `flow_bg_poll.ready`. Public `step_done` is allowed as a narrow ownership exception only for a currently-ready scoped consumer item on that bg run; ordinary bg steps remain driver-owned and rejected.

After each accepted item result, the engine either remains `awaiting_consumer` with the next ready set, pauses at a downstream gate, or re-kicks the driver if advancement exposes only engine-owned ordinary work. Cancellation leaves already-reported state durable and promotes no further items. Rehydration restores `awaiting_consumer` from persisted fanout readiness without dispatching a connector.

Mixed ready sets are partitioned by owner: the bg driver may run ordinary/engine-owned entries, while consumer entries remain poll-visible. All mutations still serialize through the run lock.

## Compose consumption mapping

| Python-era compose action | Native TS fanout action |
|---|---|
| Receive `parallel_dispatch` task list | Receive consumer item entries in `ready[]`; scoped id identifies task index |
| Create per-task worktree and run agent | Unchanged compose responsibility; use ready `do`/`agent` and local task metadata |
| Capture diff / run `pre_merge_verify` | Unchanged compose responsibility; report a local failure with `stratum_step_done` so only that item retries |
| `parallelDone(flow, step, taskResults, mergeStatus)` | One `stratum_step_done` per scoped item/stage; no aggregate call |
| `ensure_failed` / `schema_failed` subset retry | Failed scoped item reappears in `ready[]` with `previousFailure`; compose reruns only it |
| Apply the union before/around `parallelDone` | Retain successful diffs locally until fanout reaches the downstream merge gate, then apply once |
| `parallelAdvance(..., "clean")` | `stratum_gate_resolve(..., "approve")` |
| `parallelAdvance(..., conflict)` | `stratum_gate_resolve(..., "revise" | "kill")` according to the authored repair policy |
| `parallelStart` + `parallelPoll` server lifecycle | Delete: `dispatch: "engine"` is scheduled by native fanout; observe progress with `flow_poll`/`flow_bg_poll` |
| GSD `runOneStep` special parallel branch (`gsd.js:477`) | Use the same ready/step_done pump as ordinary work; retain only local progress, stuck detection, and merge-gate handling |

Compose must re-author each v0 parallel step to native fanout and add the explicit merge gate where the tasks can write. Consumer-side artifacts must be restart-safe with a **two-level identity** (AMENDED 2026-07-16; the scoped id alone is reused across runs, stages, retries, and revisions):

- The **worktree is keyed by item generation** — `(runId, <fanout>/<index>, generation)` — and lives across every stage and retry of that generation until the item terminalizes, matching engine-dispatch semantics (one worktree per item, cleanup only at item end — `engine.ts:1103`). Token-keyed worktrees would strand prior-stage filesystem state. The generation is in the key because a gate `revise` can delete and re-enumerate the whole fanout (`engine.ts:1464`): the same `<fanout>/<index>` may then denote a DIFFERENT input item. The generation is NOT the item epoch (r4 correction): epochs are restored by checkpoint revert along with the rest of `steps`, so an epoch key would collide with retained pre-revert evidence — it is the engine's run-level monotonic generation counter (see Token lifecycle), which checkpoints never roll back; descriptors expose it. Old-generation worktrees/journal entries are marked `superseded` — retained as evidence, never merged.
- **Each item yields exactly ONE cumulative diff**, captured at the item's final-stage accepted report and recorded with the `dispatchToken` of that final issuance (engine parity: engine dispatch captures a single cumulative patch only after every stage finishes — `engine.ts:1210`; per-stage diffs would re-apply earlier stages' changes when replayed in order). Intermediate stages leave their state in the item worktree; nothing per-stage is merged.
- Journal entries carry explicit states (AMENDED 2026-07-16, round 3; r4/r5-corrected): **`prepared`** → **`accepted`** → **`merged`** or **`superseded`**. A `prepared` entry is written BEFORE every `step_done` — for EVERY issuance, not only the final stage (r5): each stage/retry report journals `(dispatchToken, exact result envelope)` so recovery can re-report idempotently instead of re-executing — intermediate stages mutate the persistent item worktree and feed `${prev}` to the next stage (`engine.ts:1114`, `engine.ts:1190`), so losing their envelope would force non-idempotent re-execution in an already-mutated worktree. Only the final stage's entry also carries the item's cumulative DIFF (previous bullet); all other prepared entries are envelope-only.
- **Pre-issuance worktree witness (r6):** before executing any stage issuance, compose journals a durable pre-stage snapshot witness of the item worktree (temporary-index tree id, recorded with the issuance token). Without it, a crash after the agent mutated the worktree but BEFORE the `prepared` envelope was written would reissue the stage against a dirty worktree — the non-idempotent replay this journal exists to prevent. On restart, an issuance with a pre-stage witness but no `prepared` envelope is recovered by restoring the worktree to the witness state FIRST, then re-executing or reporting `result.failure`. `accepted` means **"this issuance terminalized the item as `succeeded`"** — NOT mere report acknowledgment: the engine evaluates output contracts and ensures after receiving a result (`engine.ts:1174`), so an acknowledged report can still yield a retry, and promoting on acknowledgment could merge a failed attempt. The engine persists **`acceptedDispatchToken`** on the terminal-succeeded item, and reconciliation matches the prepared entry's token against it: match → promote to `accepted`; the item is terminal with a DIFFERENT accepted token, or the entry's token was rotated → mark `superseded`; the issuance is still current and ready → re-report the stored envelope. On restart compose recovers worktrees and diffs from the journal, never from memory; an artifact lost to a crash before its journal write is reported as that item's `result.failure` (normal retry path) or surfaces at the gate as `revise`/`kill`.
- The merge itself is a **journaled transaction with content-addressed witnesses** (this is the "killed mid-merge" recovery case; r4-corrected to close the apply-before-witness window): BEFORE mutating anything, compose precomputes the **full expected witness chain** — the base tree id plus, for each diff in order, the expected post-apply tree id — in a **temporary index** (the existing snapshot pattern: `GIT_INDEX_FILE`-isolated `read-tree` + `git add -A` + `write-tree` at `build.js:4562`, with `apply --cached` from the anchor helper at `build.js:4544`; never touching the working tree), and journals the entire chain plus the round's `gateToken` and ordered diff list in one record. Two hard preconditions (r5): the journal and all diff/artifact metadata live OUTSIDE the merge target's tree — compose's own code notes `.compose/` is not guaranteed ignored (`build.js:4509`) and the snapshot stages everything via `git add -A`, so an in-tree journal write would invalidate the very witnesses it records; and every tree id in the chain must be UNIQUE (an empty, no-op, or net-cancelling diff makes one id ambiguous across prefix lengths) — otherwise compose aborts the transaction before mutating anything. Only then do diffs apply to the target, one at a time. Every reachable crash state therefore has a pre-journaled identity: recovery computes the current tree id (via the same temporary-index snapshot of the current working state — plain `git write-tree` hashes the index, and compose applies without `--index` over possibly-dirty state, so the snapshot pattern is normative) and matches it against the chain to determine exactly which diffs landed. No commits required (compose's merge path mutates the working tree without committing — `build.js:4354`), and no `git apply --check` (which cannot distinguish already-applied from conflict and is NOT a recovery primitive). The gate is resolved only after the transaction record is complete. On `revise`/`kill` compose restores the full journaled baseline before resolving, matching its existing conflict-rollback behavior (`build.js:4389`, `build.js:5042`). One more normative recovery rule (r6): a single `git apply` of a multi-file diff is NOT atomic (`build.js:4354`, `build.js:4364`) — a kill mid-apply leaves a partial tree matching NO witness. An unmatched tree is therefore recovered by restoring the journaled baseline, verifying its tree id, and either replaying the transaction from zero or resolving the gate `revise`/`kill`; recovery NEVER attempts to complete a partially-applied diff in place.
- Cleanup distinguishes decisions: artifacts are dropped on `approve` (after the post-merge step advances) or when the run terminalizes; a `revise` RETAINS all journal entries and diffs (now `superseded` where re-enumeration occurred) — the repair round needs the evidence.

The engine never receives diff text.

## Open questions

1. **Repair topology:** should compose standardize merge-gate `on_revise` on a single repair step, or regenerate the fanout with locally injected conflict context? The engine supports either; the first avoids rerunning successful items, while the second more closely matches today's bounce loop but can rerun the batch.
2. **Consumer filesystem attestation:** v1 deliberately rejects engine filesystem ensures against consumer worktrees. A future signed artifact/working-directory attestation could restore engine verification, but it is not required for this cutover.
3. **Mixed-owner bg readiness — RESOLVED 2026-07-15b:** deferred with the rest of background consumer dispatch. v1 rejects `dispatch: "consumer"` at `flow_run_bg` submission with a typed diagnostic and a frozen contract test (see Background flows); the mixed-owner semantics specified there bind the follow-up feature.
